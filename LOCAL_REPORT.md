## 4. The Talk-vs-Fight collision (root fix)

Before: pre-gen generated one branch per entity. The cache key was `(scene, entity)`. A user clicking "Talk to Rama" warmed the bucket; a follow-up "Fight Rama" pulled the same Talk narration. Verbs collapsed.

After: pre-gen produces `(entity × top-2 canon-allowed verbs)`. The cache key is `(scene, entity, action)`. Talk and Fight are separate cache buckets — neither shadows the other.

Cost ceiling: 8 entities × 2 verbs = 16 branches max per scene, throttled to `MAX_PARALLEL_BRANCHES` (default 2).

## 5. Action-status visibility (the dots)

Each verb in the hotspot action menu now shows:
- **green dot** — branch warmed in cache, instant tap
- **amber dot** — canon-allowed verb, not yet warmed (first tap will generate)
- **no dot** — generic fallback verb (entity has no canon entry)

These flip in real time via SSE as `pregenerate-branches` finishes its jobs.

## 8. Phase G & H summary

**Phase G shipped:**
- Sentence-level subtitle cues — narration is split on `[.!?]` boundaries and distributed proportionally over the scene's frames; the active cue is rendered with a progress dot row beneath. Fully deterministic, no extra TTS calls needed.
- Procedural mood beds — 6 ambient WAVs (serene/dramatic/somber/joyful/sacred/mysterious) generated from a tiny in-house PCM synth. Each ramayana scene is now tagged with a mood. The composition layers the bed at 0.18 volume and loops it.
- MP4 export — `POST /api/livebook/render-movie` bundles the Remotion entry, renders BookMovie at 540p with crf 28 (~17 MB for a 6:46 movie), uploads to Supabase Storage. If Supabase rejects the file (size limit, missing creds), falls back to writing `public/movies/{slug}.{hash}.mp4` and returns the relative URL. Deduped by manifest hash on both paths.
- `next.config.ts` lists the Remotion native packages as `serverExternalPackages` so Next's bundler doesn't try to inline Chromium binaries.

**Phase H shipped:**
- Six new specs cover landing copy, hotspot click, per-action cache, mobile touch, movie sentence cues, and MP4 export end-to-end.
- One real bug surfaced and was fixed: `getCtx()` and `getAudioContext()` would throw `undefined is not a constructor` on browsers without `AudioContext` (Playwright WebKit driver), crashing the entire SceneViewer. Both are now defensive.
- `data-testid` selectors added to hotspot buttons (`hotspot-{target_id}`) and verb buttons (`action-{verb}`) so tests stay stable across copy or layout edits.

## 10. Risk areas

- **Manifest endpoint hits getCachedBranch per (hotspot × verb)** — for a 4-hotspot scene with 3 verbs each that's 12 cache reads. Acceptable for now (Redis pipelined ~5–10ms total) but worth a Redis MGET if it becomes a bottleneck.
- **SSE polls the cache every 1.5s for up to 60s** — at ~12 reads/poll that's ~480 reads worst-case per stream. Acceptable on Upstash free tier; pub/sub would be cleaner if traffic grows.
- **Brain still has no UI surface** — `prepareScene` runs only when `/api/livebook/generate-scene` is called (i.e., the "Continue the Journey" path). The static reader path uses pregenerate-branches, which is now action-aware. If you want the static reader to also run brain enrichment, that's a separate wiring task.

## 15. Universality audit

User asked: are the moods, agents, and pipeline universal — or Ramayana-only?

**Universal (book-agnostic):**

| Component | Universal because |
|-----------|-------------------|
| `lib/agents/branchAgent.ts` | Verb table covers 18 universal action verbs; takes `bookTitle` + `entityType` as inputs |
| `lib/engine/branchPreGenerator.ts` | `getPregenActions(bookSlug, entityId, entityType)` reads canon when present, falls back to type defaults for any book |
| `app/api/livebook/scene-stream/[sceneId]` | Resolves scene from `ramayana` seed OR generic `bookRegistry`; mood/theme derived from text patterns, not slug |
| `app/api/livebook/stream-updates/[sceneId]` | Reads any book's hotspots via the same resolver |
| `app/api/livebook/render-movie` | Looks up by `bookSlug` via `getManifestForSlug` — any committed manifest renders |
| `lib/audio/proceduralWav.ts` | 6 abstract mood categories, no book-specific names |
| `remotion/BookMovie.tsx` | Pure manifest consumer — every render is data-driven |
| `lib/audio/musicOrchestrator.ts` | Mood-driven profile picker, with `bookSlug`/`bookTitle`/`mood`/`forceProfileId` knobs |
| `lib/data/canonLookup.ts` | Multi-book registry: `ramayana.json`, `mahabharata.json`, `panchatantra.json` |
| `LivingBookBrain.prepareScene` | Threads `bookSlug`+`bookTitle` through every step |

**Still Ramayana-leaning (intentional, not blocking universality):**

- `lib/data/scenes.ts` + `hotspots.ts` — the curated seed data is Ramayana-only. Other books register via `bookRegistry`.
- `lib/audio/soundEngine.ts` `LEGACY_SCENE_FREQS` — Ramayana scene-id → frequency table. The newer `startAmbientDroneRaw(freqs)` path is universal; the legacy table is only used when callers pass a string scene id directly. Could be deleted in a future pass.
- `components/livebook/SceneViewer.tsx` `SCENE_CHOICES` — hardcoded story-branch chips for `forest_life`, `exile`, `battle_lanka`. These never render for other books because the keys don't match. Could move to canon data later.
- `app/page.tsx` — landing showcases Ramayana imagery (`SCENE_PREVIEWS`). Marketing content; not part of the engine.

**Net:** the engine is universal end-to-end. The Ramayana-only bits are seed/marketing surface, not core behavior. A new book just needs canon JSON + a generated manifest to run on the same pipeline.
